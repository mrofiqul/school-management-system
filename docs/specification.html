School Management SaaS

Campus Specification

The complete product and technical specification for a multi-school management platform serving Bangladesh/South Asia — Android and web, built on Flutter, NestJS, and PostgreSQL. This document is the single reference the codebase is built from.

Rev v1 Date 2026-10-04 Scope Multi-tenant SaaS Stack Flutter · NestJS · PostgreSQL Region Bangladesh / South Asia
01

Overview & scope

A unified platform that digitizes day-to-day school operations — admissions, attendance, academics, fees, communication, reporting — sold as a subscription to many schools rather than built for one.

Four audiences are served directly: the Super Admin (the platform owner, managing every school as a tenant), the School Admin (one school's full control), the Teacher, and the Student/Parent pair sharing one mobile app with role-conditional navigation.

Scope was deliberately narrowed to multi-school SaaS over a single-school build, because the tenancy and billing concerns it adds (Super Admin role, subscription plans, per-tenant branding) are far cheaper to design in from the start than to retrofit later.
02

User roles

Six roles, five of which are scoped to exactly one school; the Super Admin is scoped to none.

Super Admin
Platform owner. Onboards schools, manages subscription plans and platform billing, platform-wide analytics. No school_id.
School Admin / Principal
Full control of one school — classes, staff, fees, policies, reports.
Teacher
Attendance, gradebook, homework, timetable, messaging, leave requests.
Student
Views timetable, homework, grades, attendance, fee status, notices. Read-only on fees.
Parent
Monitors one or more children, pays fees, messages teachers, receives alerts.
Accountant / Staff
Optional role sharing School Admin's fee endpoints — collection, payroll, inventory.
03

Feature modules

Grouped the way the data model and API group them — not by department, but by what shares a foreign key.

Academic

  • Admission & enrollment, with document uploads
  • Class / section management, subject mapping
  • Timetable builder with conflict detection
  • Attendance — daily and period-wise, teacher-marked, offline-queued
  • Gradebook & exam management — marks entry, computed report cards, grading scale
  • Homework / assignments — post, submit, grade
  • Syllabus tracker, study materials, notice board

Administrative

  • Staff management — profile, leave, payroll-lite
  • Fee management — per-class structure, invoices, online payment, receipts, dues
  • Transport management — routes, vehicles, driver info Phase 3
  • Library management — catalog, issue/return, fines Phase 3

Communication

  • Push, SMS, and email alerts — fee due, exam results, notices
  • In-app messaging — teacher ↔ parent only
  • Events / academic calendar

Platform (Super Admin only)

  • Tenant onboarding — self-serve or sales-assisted
  • Subscription & plan management, usage-limit enforcement
  • Per-tenant branding on report cards, receipts, the parent app view
  • Platform billing, separate in the data model from school-to-parent fee billing
04

Phasing

Dependency order, not feature priority — each phase is buildable on what the previous one shipped.

PHASE 1
MVPTenant onboarding (manual) → School setup → Attendance → Timetable → Basic gradebook → Notices → Student/Parent view-only login. Fees tracked manually, no online payment yet.
PHASE 2
Payments & engagementSSLCommerz/bKash/Nagad fee payments, homework/assignments, exam & report cards, SMS + push notifications, subscription billing enforcement.
PHASE 3
OperationsTransport, library, HR/payroll-lite, per-tenant branding, analytics dashboards, self-serve signup.
PHASE 4
ScaleiOS app, biometric/QR attendance, at-risk student flagging, performance analytics.

Data model

Four domains sit on one tenancy & identity foundation. Every table outside the platform-billing pair carries school_id, enforced server-side — never trusted from a client.

  • Junction tables use a surrogate id plus a unique constraint on the pair, rather than a composite primary key.

API reference

REST, versioned under /v1. A bearer JWT carries sub, school_id, role, exp — school_id is read from the token only, never from a request body or query string.

MethodPathWhoDoes
POST/auth/loginpublicIssues access + refresh token
GET/platform/schoolsSAList tenants
POST/platform/schoolsSAOnboard a school + first admin
POST/studentsADAdmit — creates User + StudentProfile
POST/attendanceTCBulk-mark one timetable slot
POST/exam-schedules/:id/marksTCBulk marks entry
GET/students/:id/report-cardAD PA STComputed, never stored
POST/invoices/:id/checkoutPAStart hosted gateway payment
POST/payments/webhook/:gatewaygatewaySigned server-to-server settlement
GET POST/noticesAD TCRead for all; post for staff

Full 45-endpoint reference across 8 resource groups — Auth, Platform, Tenancy & People, Academics, Attendance, Exams/Grades/Assignments, Fees & Billing, Communication — lives in the Campus API artifact (see Reference Artifacts). List responses wrap as {"{"} data, meta: {"{"} page, per_page, total {"}"} {"}"}; errors as {"{"} error: {"{"} code, message, status {"}"} {"}"}.

07

Applications & screens

Four surfaces, one backend. Each is fully sketched as an interactive artifact — this section summarizes what each one covers.

Campus Owner Console — web, Super Admin

Platform-wide Overview (growth, MRR, signups), Schools (list + usage/plan detail panel), Plan tiers, cross-tenant Billing, Audit Log.

Campus School Console — web, School Admin

Dashboard (today's attendance, fee collection, next exam), Students, Staff, Timetable grid, Fees, Notices. White-labeled per school.

Campus App — Flutter, Student & Parent

One app, role-conditional bottom nav: Student gets 4 tabs (no Messages — the endpoint itself denies that role), Parent gets 5. Home surfaces actionable cards rather than a menu; Assignment Detail is one route branching on role, not two screens.

Campus App — Flutter, Teacher

Attendance marking (bulk, three-way P/A/L toggle, offline-queued) and marks entry are the two highest-frequency screens — both designed around one repeated gesture rather than a form per student.
